## Current Tool

The working inference operations tool is a Bun + TypeScript menu at
`bin/api-v2/docker/tool/`:

```bash
cd bin/api-v2
./docker/tool/run
```

It currently owns:

- local CPU/GPU acquisition sidecars
- model warmup and cache inspection
- cache export/import
- vendor-compatible standalone builds
- native Lambda image builds
- local smoke and real-image tests
- ECR pushes with immutable tags
- SAM/CloudFormation deployment
- frame-grabber container/Lambda operations
- cleanup and container logs

## Important Commands

### Status

Reports container health, cache size, active model paths, manifests, and local
image availability. It is read-only.

### Start CPU/GPU

Starts the official acquisition server and one-shot warmup container. The
warmup downloads the selected package and captures `model-metadata.json`.

### Build standalone image

Requires an offline-complete cache, including the captured package manifest,
and produces `chalkysticks/inference:latest`. This is the large
vendor-compatible artifact/debug image, not the Lambda runtime.

### Build Lambda image

Reads the active model and captured manifest from the standalone image, selects
the ONNX package, resolves its content-addressed blobs, and copies only:

- `weights.onnx`
- `inference_config.json`
- `class_names.txt`

into the small native `linux/arm64` image. It produces
`chalkysticks/inference:lambda` and does not include Roboflow or PyTorch.

### Push to ECR

Reads `CHALKYSTICKS_ECR_REPO` from `bin/api-v2/.env`, logs in to ECR, and
publishes both `latest` and an immutable UTC timestamp tag.

### Deploy to AWS Lambda

The deployment command:

1. Resolves ECR `latest` to an immutable digest.
2. Checks the optional `scan.chalkysticks.com` certificate.
3. Runs `sam build` and non-interactive `sam deploy`.
4. Updates Lambda and CloudFront through CloudFormation.
5. Prints the direct, CloudFront, and custom endpoints.

If the custom-domain certificate is pending, CloudFront remains live on its
AWS hostname and the alias is deferred until the next deployment.

### Cleanup

Stops local sidecars and removes the model cache volume after confirmation.
This is destructive to local acquired packages but does not alter Lambda, ECR,
or Roboflow.

## Configuration

The tool reads `bin/api-v2/.env` without sourcing it:

```dotenv
ROBOFLOW_API_KEY=...
ROBOFLOW_DETECTION_MODEL_URL=http://127.0.0.1:9001/balls-and-pockets-qi5jc/4
ROBOFLOW_WARMUP_MODELS=balls-and-pockets-qi5jc/4

CHALKYSTICKS_ECR_REPO=172720370877.dkr.ecr.us-east-2.amazonaws.com/chalkysticks/roboflow-table-detection
CHALKYSTICKS_INFERENCE_CUSTOM_DOMAIN=scan.chalkysticks.com
CHALKYSTICKS_INFERENCE_CERTIFICATE_ARN=arn:aws:acm:us-east-1:172720370877:certificate/68e4e42c-1cd0-4b27-913a-ccce954f4245
```

The active native builder requires one combined
`ROBOFLOW_DETECTION_MODEL_URL`. Legacy dual-model variables remain fallback
inputs for local/older workflows.

## Global `chalky` CLI

The machine-wide CLI lives at:

```text
prototypes/53-chalky-cli
```

It is installed globally as `chalky`, discovers the ChalkySticks workspace,
supports both interactive and scriptable commands, and already uses a safe
execution pattern for SDK publishing: dry-run by default, with mutation
requiring `--execute --yes`.

That makes it the correct long-term frontend for cross-project inference
operations. The local `docker/tool` should remain the implementation reference
until its operations are extracted or wrapped without duplicating deployment
logic.

## Global `chalky inference` Commands

### Available Now: read-only operations

```bash
chalky inference status
chalky inference status --json
chalky inference health
chalky inference health --endpoint cloudfront
chalky inference health --endpoint origin
chalky inference logs --since 15m
chalky inference certificate
chalky inference certificate --json
chalky inference tool
```

`scan` is an alias for `inference`. These commands do not change models or AWS
resources. `status` combines CloudFormation, Lambda, CloudFront, and ACM state;
`health` probes the custom, distribution, and origin endpoints concurrently;
and `logs` reads the Lambda CloudWatch log group. The status, health, and
certificate commands exit non-zero when unhealthy and support JSON where shown
for automation.

`chalky inference tool` is the bridge to the existing menu-driven implementation
for local builds and deployments. It intentionally does not duplicate those
mutating operations in the global CLI.

Current `health` checks:

- ACM certificate status
- CloudFront distribution status
- CloudFront health response
- direct Lambda origin response
- Lambda state and last update status
- deployed ECR digest

Direct DNS diagnostics and an optional real-image contract check remain useful
next read-only additions.

### Phase 2: explicit release stages

```bash
chalky inference model plan --model balls-and-pockets-qi5jc/5
chalky inference model acquire --model balls-and-pockets-qi5jc/5 --execute --yes
chalky inference build --execute --yes
chalky inference push --execute --yes
chalky inference deploy --execute --yes
chalky inference release --model balls-and-pockets-qi5jc/5 --execute --yes
```

`release` should orchestrate the same stages, not introduce a second
implementation. It should print/checkpoint:

1. current deployed digest/tag
2. requested model slug/version
3. manifest acquisition
4. official model tests
5. standalone build
6. native build
7. parity gate
8. ECR immutable tag/digest
9. CloudFormation status
10. public health/inference verification

### Phase 3: rollback and lifecycle

```bash
chalky inference releases
chalky inference rollback --tag 2026-08-02T20-40-37 --execute --yes
chalky inference disable --execute --yes
chalky inference enable --execute --yes
chalky inference destroy --plan
chalky inference destroy --execute --yes
```

Rollback and destruction should require stronger confirmation than ordinary
deployment and print exactly which stack, function, distribution, model path,
and ECR image will change.

## CLI Design Rules

1. Read-only commands must work without confirmation and support `--json`.
2. Every mutation should be a dry run unless `--execute --yes` is present.
3. Destructive commands should name resources explicitly and require an
   additional typed confirmation in interactive mode.
4. The CLI should call AWS/Docker with argument arrays, not interpolated shell
   strings containing user input.
5. Roboflow keys remain in local environment/config and must never appear in
   command history or logs.
6. Model releases should be resumable by stage; a failed deploy should not
   require re-downloading or rebuilding a verified model.
7. Native/vendor parity remains a hard gate for compatible-model releases.
8. CloudFormation remains the only supported Lambda/CloudFront update path.
9. Health checks should distinguish DNS, certificate, edge, origin, runtime,
   and model failures instead of returning one generic red status.
10. The CLI should record a machine-readable release receipt containing model,
    manifest hashes, ECR digest/tag, stack update, and verification timings.

## Migration Strategy

The cheapest first bridge is a `chalky inference tool` command that launches
`bin/api-v2/docker/tool/run` from the discovered workspace. Read-only native
commands can then move into `chalky` one at a time.

Before implementing the full release command, extract reusable acquisition,
build, ECR, and SAM operations from the interactive tool so both frontends call
the same functions. Avoid maintaining two independent versions of the model
release algorithm.
