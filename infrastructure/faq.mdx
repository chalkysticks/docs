## Common Scenarios

### I updated my Roboflow model and it has a new version number. How do I update?

1. Update the version number in `bin/api-v2/.env`:
   ```bash
   # Old
   ROBOFLOW_MODEL_URL=http://127.0.0.1:9001/my-first-project-2-qvkxb/8
   # New
   ROBOFLOW_MODEL_URL=http://127.0.0.1:9001/my-first-project-2-qvkxb/9
   ```
2. Restart PHP-FPM (or your queue workers)
3. The first `tableScanFull` call triggers the sidecar to download the new model version into the existing cache. Takes a few seconds, then cached forever.

If you also built a standalone image (Option B), you need to re-warm and rebuild:

```bash
./docker/tool/run
# → Stop everything
# → Cleanup (wipes old cache)
# → Start (CPU) (re-warms with new model)
# → Build standalone image (bakes new cache into image)
```

### How does the inference sidecar hook into the Laravel API?

`Services\Roboflow` reads `ROBOFLOW_MODEL_URL` from `config/services.php`, which reads it from `.env`. The service POSTs a base64-encoded image to that URL with `api_key`, `confidence`, and `overlap` as query params. The sidecar speaks the exact same HTTP contract as `serverless.roboflow.com`, so switching is a pure env-var swap with zero code changes.

Key files:
- `app/Services/Roboflow.php` — the HTTP client
- `config/services.php` (lines 58-71) — model URL defaults
- `app/Http/Controllers/v3/Data.php` — `tableScanFull` method (creates two Roboflow service instances, one per model)

### How do I test if the sidecar is working?

**Quick smoke test (no real image needed):**

```bash
./docker/tool/run
# → Test inference (smoke)
```

This POSTs a 1x1 transparent PNG to each model. If you get `HTTP 200`, the sidecar is alive and serving.

**Real inference test with an actual pool table photo:**

```bash
KEY=$(grep '^ROBOFLOW_API_KEY=' .env | cut -d= -f2-)
base64 -i /path/to/table.jpg | curl -sS -X POST \
    -H 'Content-Type: application/x-www-form-urlencoded' \
    --data-binary @- \
    "http://localhost:9001/my-first-project-2-qvkxb/8?api_key=$KEY&confidence=0.4&overlap=0.3" | jq
```

Expected: a JSON object with `predictions` array containing Ball, Pocket, and Rail detections with confidence scores and bounding boxes.

**End-to-end test through the Laravel API:**

```bash
curl -F image=@/path/to/table.jpg http://localhost:8000/v3/data/table-scan-full | jq
```

### How do I compare sidecar results against Roboflow's hosted API?

```bash
# Get sidecar results
curl -F image=@table.jpg http://localhost:8000/v3/data/table-scan-full | jq > sidecar.json

# Temporarily switch to serverless.roboflow.com in .env, restart PHP
curl -F image=@table.jpg http://localhost:8000/v3/data/table-scan-full | jq > serverless.json

# Diff
diff <(jq -S . sidecar.json) <(jq -S . serverless.json)
```

Expected: structurally identical — same prediction count, same `ball_type` assignments, coordinates within floating-point drift.

### Can I run the sidecar on a remote server?

Yes. The standalone image (`chalkysticks/inference:latest`) runs anywhere Docker runs:

```bash
# On the remote host
docker run -d --name chalkysticks-inference -p 9001:9001 chalkysticks/inference:latest

# In your Laravel .env (on the API server)
ROBOFLOW_MODEL_URL=http://<remote-host>:9001/my-first-project-2-qvkxb/8
ROBOFLOW_BALLDETECTION_MODEL_URL=http://<remote-host>:9001/ball-detection-feb-2026/11
```

### How do I ship the standalone image to another machine?

```bash
# On the build machine
docker save chalkysticks/inference:latest | gzip > chalkysticks-inference.tar.gz

# Transfer (scp, rsync, S3, USB, whatever)
scp chalkysticks-inference.tar.gz user@remote:/tmp/

# On the target machine
gunzip -c /tmp/chalkysticks-inference.tar.gz | docker load
docker run -d -p 9001:9001 chalkysticks/inference:latest
```

## Troubleshooting

### `Model type not supported: ('object-detection', 'rfdetr-nano')`

You're using the wrong base image. The dedicated `roboflow-inference-server-arm-cpu` image strips PyTorch, and our RF-DETR models need PyTorch. Use the full `roboflow-inference-server-cpu` image instead (which is the default in our Dockerfile).

### Warmup says `ROBOFLOW_API_KEY is empty; skipping warmup`

`bin/api-v2/.env` is missing or doesn't define `ROBOFLOW_API_KEY`. The warmup exits 0 (skip) so it doesn't block the inference server, but the cache won't be pre-populated — the first real request will trigger the download instead.

### Service worker says "offline cache disabled" on mobile

Service workers require HTTPS (secure context). `localhost` is exempt, but LAN IPs like `http://192.168.1.88:61350` are not. Either use Chrome's `chrome://flags/#unsafely-treat-insecure-origin-as-secure` flag, or serve over HTTPS (e.g., via cloudflared tunnel).

### Docker says "no space left on device" during Lambda image build

Each iteration of "Build Lambda image" creates ~9 GB of dangling images. Run `docker image prune -f` and `docker builder prune -af` to reclaim space. The tool now auto-prunes before and after each Lambda build, but if you hit this from a manual build, that's the fix.

### CloudFormation stack is in `UPDATE_ROLLBACK_FAILED`

This happens when `aws lambda update-function-code` (an out-of-band update) makes CloudFormation's recorded state diverge from actual state. Fix:

```bash
aws cloudformation continue-update-rollback \
  --stack-name chalkysticks-inference \
  --region us-east-2

# If that also fails, skip the problematic resource:
aws cloudformation continue-update-rollback \
  --stack-name chalkysticks-inference \
  --region us-east-2 \
  --resources-to-skip InferenceFunction
```

Then redeploy with `sam deploy` through the tool.

### Lambda returns `Error in cpuinfo: failed to parse the list of possible processors`

Lambda's container sandbox doesn't expose `/sys/devices/system/cpu/possible`. The fix is `LD_PRELOAD=/opt/cpuinfo-shim.so` which intercepts `open()` calls for those paths and returns a memfd with `"0-1\n"`. This is already baked into `Dockerfile.lambda`. If you're building a Lambda image from scratch, make sure the shim is compiled and preloaded.

### Lambda returns 404 with Go-style `text/plain` body

Port conflict. Lambda's runtime API binds `127.0.0.1:9001`. If your app also binds 9001, it silently fails (EADDRINUSE), and LWA's readiness check connects to Lambda's runtime API instead. Fix: use port 8080 for the app (already set in `Dockerfile.lambda`).

### Lambda returns 503 after 30 seconds

Cold start is taking longer than the function timeout. The 9.6 GB image + Python imports take 25-40 seconds. If you're using API Gateway HTTP API, it has a hard 30s timeout cap. Switch to a Lambda Function URL (no timeout cap) or increase the function Timeout.

### Sidecar boots locally but crashes in Lambda

Common causes we've seen:

1. **PyTorch can't find CUDA libs** — don't delete `nvidia/` from the image; PyTorch dlopens `libcudart.so` at import time even on CPU
2. **cpuinfo can't read /sys** — use the LD_PRELOAD shim
3. **asyncua / mediapipe / etc. missing** — Roboflow's `blocks_loader` eagerly imports all enterprise workflow blocks at startup; you can't strip any library that backs a workflow block
4. **uvicorn on wrong port** — use 8080, not 9001

### How do I check what's actually running inside the inference container?

```bash
# Container logs
docker logs chalkysticks-inference --tail 50

# Running processes
docker top chalkysticks-inference

# Cache contents
docker exec chalkysticks-inference ls -la /tmp/cache/
docker exec chalkysticks-inference du -sh /tmp/cache/shared-blobs/

# Python site-packages (useful for debugging missing deps)
docker run --rm chalkysticks/inference:latest du -sh \
  /usr/local/lib/python3.11/site-packages/* | sort -h | tail -25
```

## What We Learned

1. **Roboflow's CPU inference image bundles ~5 GB of unused ML frameworks** (nvidia CUDA libs, triton GPU JIT, jaxlib, etc.) for features we don't use (CLIP, SAM, VLMs, LLMs). The `arm-cpu` slim variant strips these but also strips PyTorch, which our RF-DETR models need.

2. **Lambda port 9001 is reserved** for the Lambda runtime API. Never bind an application to port 9001 inside a Lambda container.

3. **Docker layer model bites hard when stripping images.** `RUN rm -rf` in a Dockerfile creates tombstone layers but doesn't actually shrink the image. The only way to truly remove content is `docker export | docker import` (flatten to a single layer) or multi-stage `COPY --from` into a fresh base.

4. **Lambda's `/sys/devices/system/cpu/` is not exposed.** Any ML library that uses `cpuinfo` for CPU topology detection will crash. `LD_PRELOAD` with an interceptor shim is the cleanest workaround.

5. **SAM doesn't see diffs when the ImageUri parameter string is unchanged.** If you push a new `:latest` to ECR, you must resolve the digest and pass `repo@sha256:DIGEST` as the SAM parameter for CloudFormation to detect a change.

6. **The Roboflow inference server eagerly imports ALL enterprise workflow blocks at startup.** If any block's dependency is missing, the entire server fails to boot. You can't selectively strip libraries without understanding Roboflow's import tree.
