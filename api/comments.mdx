---
title: 'Comments'
description: 'Polymorphic comments across all entity types'
---

Comments attach to a number of entity types: venues, user media, venue media, users, content, facts, and diagrams. Listings are exposed under the parent entity, while create/update/delete/flag live under `/v3/comments`.

## List All Comments

Generic flat index with filters.

```bash
GET /v3/comments
GET /v3/comments?entity_type=venue&entity_id=1
```

The aggregate feed can mix parents with different visibility rules, so it is deliberately restricted and never stored in shared cache. Prefer a parent-scoped listing when the parent is known.

## List By Parent

Per-entity comment listings:

```bash
GET /v3/users/{user}/comments
GET /v3/venues/{venue}/comments
GET /v3/venues/{venue}/media/{media}/comments
GET /v3/media/{media}/comments
GET /v3/diagrams/{hash}/comments
GET /v3/content/{content}/comments
GET /v3/facts/{fact}/comments
```

Public parent-scoped listings are cacheable, including their public `include`
parameters. For example:

```bash
GET /v3/content/240/comments?include=user,children
GET /v3/venues/635/comments?include=user,children
```

## Create Comment

```bash
POST /v3/comments
Authorization: Bearer YOUR_TOKEN
```

**Request:**
```json
{
  "entity_type": "venue",
  "entity_id": 1,
  "body": "Great place to play!"
}
```

## Update Comment

```bash
PUT /v3/comments/{comment}
Authorization: Bearer YOUR_TOKEN
```

**Request:**
```json
{
  "body": "Edited comment text"
}
```

## Delete Comment

```bash
DELETE /v3/comments/{comment}
Authorization: Bearer YOUR_TOKEN
```

## Cache Invalidation

Create, update, and delete events enqueue targeted surrogate-key purges. A comment on content `240` invalidates the comment key, `co.240.c` relationship key, and `co.240` parent key. That refreshes both `/content/240/comments` and any cached content response that embeds comments.

Parent invalidation is intentional even for an empty list or deletion of the last item; the newly created or deleted comment may not have existed in the old response's key set.

Purges run through Laravel's queue and invalidate both Varnish trust partitions. A short queue-processing delay is possible after a successful write.

## Flag Comment

Report a comment for moderator review.

```bash
POST /v3/comments/{comment}/flag
Authorization: Bearer YOUR_TOKEN
```

**Request:**
```json
{
  "reason": "spam"
}
```
